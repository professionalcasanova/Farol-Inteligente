# Wave de Issues - fechamento da beta v1.1

Data de consolidacao: 2026-04-10

## Posicionamento tecnico

- Chamar esta rodada de `v1.1` faz sentido. O feedback aponta fechamento de gaps importantes de produto e UX sobre uma base ja existente, nao uma mudanca de plataforma que justificaria `v2`.
- O ambiente publicado passa a ser homologacao. PRs podem continuar existindo, mas aprovacao e merge devem acontecer somente depois de validacao local completa.
- Nem todo feedback recebido representa ausencia total de backend:
  - multiplas contas ja existem na API e nos testes; o gap atual esta na exposicao e gestao desse fluxo no frontend.
  - transacoes ja possuem edicao dedicada em `Movimentacoes`.
  - `Contas a pagar` ainda nao possuem edicao e exclusao.
- Correcao importante de dominio: `PIX` nao deve ser tratado como categoria principal de gasto. Isso e meio de pagamento ou trilha da transacao. Categoria deve continuar respondendo ao "com o que gastei/recebi?" e nao "como paguei/recebi?".

## Eixos priorizados

### 1. Contas financeiras
- O dashboard hoje so oferece criacao de conta quando o usuario ainda nao tem nenhuma.
- Para a beta de homologacao, o produto precisa expor claramente criacao de mais de uma conta e selecao consciente da conta no registro de movimentacoes.

### 2. CRUD operacional
- O produto ja avancou para um ponto em que erro humano precisa ser tratado como fluxo normal.
- A prioridade pratica e completar edicao onde ela ainda nao existe ou esta escondida demais:
  - contas a pagar
  - planejamento mensal
  - lancamentos manuais iniciados no dashboard

### 3. Responsividade mobile web
- O screenshot mostra perda de enquadramento no iPhone, com navegacao e conteudo extrapolando a largura util.
- Isso nao pede app nativo agora; pede endurecimento de layout mobile web, especialmente `AppShell`, cabecalho, navegacao e blocos com grids largos.

### 4. Taxonomia financeira brasileira
- As categorias seed atuais ainda sao enxutas para uso real.
- O ajuste correto e revisar categorias padrao para contexto brasileiro e, separadamente, decidir se vale introduzir um campo futuro de meio de pagamento.

## Issues propostas

### 1. Expor gestao de multiplas contas no fluxo principal
- Tipo: improvement
- Prioridade: high
- Areas: frontend, backend, tests, ux
- Resumo:
  - Expor criacao de conta adicional mesmo quando ja existir ao menos uma conta.
  - Tornar a selecao de conta mais explicita no dashboard e nos fluxos de registro/importacao.
  - Reaproveitar a API atual de contas em vez de reimplementar suporte do zero.

### 2. Adicionar CRUD real para contas a pagar, incluindo ocorrencias recorrentes e parceladas
- Tipo: feature
- Prioridade: high
- Areas: backend, frontend, tests, ux
- Resumo:
  - Adicionar update e delete para contas avulsas.
  - Definir como editar ocorrencias vindas de series recorrentes ou parceladas sem quebrar consistencia da serie.
  - Tratar pagamento/despagamento como parte do fluxo, nao como substituto de edicao.

### 3. Fechar o gap de edicao operacional em planejamento e lancamentos
- Tipo: improvement
- Prioridade: high
- Areas: frontend, backend, tests, ux
- Resumo:
  - Tornar o planejamento mensal claramente editavel como snapshot do mes.
  - Dar continuidade de edicao para lancamentos criados pelo dashboard, redirecionando ou expondo caminho evidente para ajuste posterior.
  - Avaliar delete pontual para transacoes como parte do CRUD minimo.

### 4. Corrigir responsividade mobile web para iPhone Safari
- Tipo: bug
- Prioridade: high
- Areas: frontend, tests, ux
- Resumo:
  - Eliminar estouros horizontais e componentes fora da viewport.
  - Revisar navegacao principal, bloco de usuario, header e grids em telas estreitas.
  - Garantir navegacao e leitura aceitaveis sem depender de app nativo.

### 5. Expandir taxonomia financeira brasileira sem confundir categoria com meio de pagamento
- Tipo: improvement
- Prioridade: medium
- Areas: backend, frontend, tests, ux
- Resumo:
  - Revisar categorias padrao com foco em realidade brasileira.
  - Nao modelar `PIX` como categoria de orcamento/gasto.
  - Se necessario, abrir espaco futuro para um campo separado de meio de pagamento ou origem da movimentacao.

## Sequenciamento sugerido

1. Responsividade mobile web
2. Gestao de multiplas contas
3. CRUD de contas a pagar
4. Edicao operacional de planejamento e lancamentos
5. Revisao de taxonomia brasileira

## Tradeoffs

- Tratar `PIX` como categoria seria mais rapido, mas pioraria analise financeira e orcamento logo no MVP.
- Expor multiplas contas agora aumenta um pouco a complexidade visual, mas evita um bloqueio basico de uso real.
- CRUD de recorrencia exige cuidado para nao confundir "editar esta ocorrencia" com "editar a serie inteira"; vale explicitar esse contrato na issue e na UX.
